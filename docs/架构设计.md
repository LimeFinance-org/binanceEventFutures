# 架构设计

## 1. 总体结构

```
                    ┌──────────────────────── 训练侧（GPU，子进程，可断点恢复）────────────────────────┐
data.binance.vision │                                                                                  │
   历史归档  ──────▶│ 数据同步 ─▶ 1分钟面板 ─▶ 特征/通道 ─▶ 特征研究 ─▶ 模型搜索 ─▶ 样本外验证 ─▶ 选择 │
                    │  archive     dataset      features     screen      studies     finalize    select │
                    │                                                                         │        │
                    │                    消融实验 ◀─────────────────────────────────────────┤        │
                    │                    独立测试集评估（台账）─▶ 组合回测/压力测试 ─▶ 版本登记 ─┘        │
                    └──────────────────────────────────────────────────────────────────────┬───────────┘
                                                                                           ▼
                                                                              模型版本库 registry/
                                                                              （冠军指针 + 回退历史）
                                                                                           │
 币安公开行情 REST ─▶ 实时缓冲 ─▶ 同一份面板/特征代码 ─▶ Predictor ─▶ 信号策略 ─▶ 全局风控 ─▶ 预测记录库
   （每分钟）          LiveBuffer                         （校准后概率）  Policy     RiskManager   SQLite
                    └────────────────────── 实时侧（CPU，独立进程，绑定专用核心）──────────────────────┘
                                                                                           │
                                        中文 Web 控制台（FastAPI）◀────────────────────────┘
```

训练侧和实时侧只通过磁盘上的**模型版本库**和 **SQLite** 交换信息，没有共享内存或共享进程，
所以训练占满 GPU 和大部分 CPU 时，实时预测的延迟不受影响。

## 2. 时间约定与防泄漏

这是整个系统正确性的基础，所有模块遵守同一约定：

- 一根 `open_time = T` 的 1 分钟 K 线在 `T + 60s` 收盘；
- 面板以**决策时刻** `ts = T + 60s` 为索引，`ts` 行只包含此刻已经收盘、已经发布的数据；
- 资金费率在结算时刻之后才可见；持仓量指标加 6 分钟发布延迟保护；
- 标签 `y[ts] = sign(指数价[ts + h] − 指数价[ts])`，平局不参与训练。

防泄漏的四道保障：

| 保障 | 位置 | 做法 |
|---|---|---|
| 特征只用有限回看窗口 | `features/core.py` | 不用 EWM / expanding / 全局归一化；高周期 K 线只用已收盘部分 + 当前 K 线截至此刻的部分 |
| 截断不变性检验 | `features/leakage.py` | 在随机时刻截断数据重算特征，截断点之前的值必须不变；训练前自动执行，不通过则中止 |
| 实时/离线一致性 | `features/leakage.py`、测试 | 只用最近 4500 分钟缓冲算出的特征必须等于全历史算出的特征；回放测试验证概率一致 |
| 单特征可疑预测力 | `features/leakage.py` | 单个特征 AUC 超过 0.60 判定为疑似泄漏并中止（真实行情约 0.52~0.54） |

验证切分（`validation/splits.py`）：

```
|◀──────────────────────── 开发区间 ────────────────────────▶| purge |◀─ 独立测试集（最后 90 天）─▶|
   训练 … | purge | 早停 | purge | 验证折1 | 验证折2 | … | 验证折K |
```

- 每一折：训练段 → purge → 早停段 → purge → 验证折，purge = 预测期限 + embargo(60 分钟)；
- 超参搜索用轻量 walk-forward（3 折），候选模型再做完整 walk-forward（10 折）；
- 独立测试集只在 `holdout` 阶段读取，访问记入台账（`runs/holdout_ledger.json`），同一窗口默认只允许一次。

## 3. 特征：数据源 × 特征族 × 时间尺度

每个特征带三元组元数据 `(source, family, scale)`，后续的筛选、搜索、消融都按这三个维度进行。

- **数据源**：指数价、现货、永续合约、标记价、溢价指数、资金费率、持仓量/多空比、跨品种、时间；
- **时间尺度**：3 / 5 / 10 / 15 / 30 / 60 / 120 / 240 / 480 / 1440 分钟的滚动窗口，加上对齐的 5m/15m/1h/4h/1d K 线；
- **特征族**：收益、波动率、动量、区间位置、效率比、成交量、主动买卖失衡、成交强度、基差、VWAP 偏离、溢价 z 值、持仓量变化等。

默认约 350 个特征、320 个分组。序列模型另外使用 12 个逐分钟通道（标准化收益、量、失衡、基差等）。

"哪些周期/数据源有效"由三层实验回答，结果都在控制台「特征与周期」页：

1. **特征研究**：LightGBM 增益排序（细粒度分组）+ 按数据源/周期/特征族的联合置换重要性，统计跨折稳定性；
2. **搜索**：用多少个分组、最长用到哪个周期、启用哪些数据源，本身就是 Optuna 的搜索维度；
3. **消融**：对最佳树模型逐个去掉数据源、限制最长/最短周期，看样本外损失的变化。

## 4. 模型库与搜索空间

| 模型族 | 输入 | 任务范围 | 复杂度等级 | 设备 |
|---|---|---|---|---|
| logreg（简单基线） | 表格特征 | 单任务 | 0 | CPU |
| lightgbm | 表格特征 | 单任务 | 1 | CPU |
| xgboost | 表格特征 | 单任务 | 1 | GPU |
| mlp | 表格特征 | 多期限 × 共享/单币种 | 2 | GPU |
| gru / tcn / transformer | 分钟序列 + 可选表格特征 | 多期限 × 共享/单币种 | 3 | GPU |
| multiscale（多尺度融合） | 1/5/15/30 分钟多路序列 + 可选表格特征 | 多期限 × 共享/单币种 | 4 | GPU |
| ensemble | 以上模型的 logit 加权 | 单任务 | 5 | — |

- 神经网络都是多任务结构（每个期限一个输出头），并分别以"两币种共享"和"每币种独立"两种作用域搜索，
  由排行榜决定哪种更好；
- 多尺度模型融合哪些尺度、每路用 GRU/TCN/Transformer 哪种编码器，也是搜索维度；
- 目标函数是各折**样本外对数损失**的均值，逐折上报并用 MedianPruner 剪枝；
- 预算：`search.time_budget_hours` 按各 study 的试验数比例分配；GPU 上的 study 可以多进程并行
  （`search.parallel_workers`），共享同一个 Optuna JournalStorage。

## 5. 模型选择

对每个任务：

1. 每个 study 的最佳试验进入候选（保证逻辑回归基线一定在内），做完整 walk-forward 得到样本外预测；
2. **集成**：贪心集成选择只在前半部分折上确定权重，再与单模型一起在后半部分折上比较；
3. **简单优先**：按复杂度从低到高，更复杂的模型只有当"逐样本对数损失之差"的区块自助法置信下界 > 0 时才替换当前选择；
4. **概率校准**：不校准 / Platt / 等渗回归三选一，按前向链式（第 k 折只用 <k 折拟合）的对数损失决定；
5. **信号策略**：在校准后的样本外概率上选择阈值和市场状态过滤（见下节）；
6. **PBO**：用候选 × 折的表现矩阵计算回测过拟合概率。

## 6. 信号策略

置信度 `c = max(p, 1−p)`，`c ≥ 阈值` 且市场状态未被过滤时发出 HIGHER/LOWER，否则 NO_TRADE 并记录原因。

阈值选择规则（`signals/policy.py`）：

1. 可行性：覆盖率、信号数、去重叠有效样本数、跨折稳定性都达到配置下限；
2. 若有阈值的胜率置信下界 ≥ 70% → 取其中覆盖率最高者（`target_met`）；
3. 否则取"按置信下界计算的期望收益 × 覆盖率"最大且为正者（`positive_ev`）；
4. 都没有 → 该任务不开仓（`no_edge`）。

市场状态过滤（波动率三分位、趋势/震荡、交易时段、周末）只有在带来明确改进时才采用。

重叠样本的处理：每分钟滚动的 10/30 分钟合约彼此高度重叠，胜负不独立。所有置信区间使用**按时间块重采样的自助法**，
并同时报告有效样本量和"去重叠子样本"胜率。

## 7. 全局风控

`risk/manager.py` 只接收"开仓提议"（币种、期限、方向、胜率估计、赔率），不接触模型。检查项：

- 赔率可靠且未过期；期望收益 `p × 赔率 − (1 − p)` 不低于下限；
- 单笔金额在平台允许范围内；未到期持仓数、未到期本金总额、单币种本金；
- **相关性加权的同向敞口**（同币种权重 1，BTC/ETH 之间按相关系数加权；反向持仓相互抵消）；
- 同一任务的最小开仓间隔（限制持仓重叠）；连续同向开仓次数；
- 每日亏损上限（已实现亏损 + 未到期本金，UTC 00:00 重置，与平台口径一致）；连续亏损冷静期。

回测（`backtest/simulator.py`）和实时服务使用同一个 RiskManager 类。

## 8. 实时服务

每分钟收盘后约 1.5 秒触发一轮：增量取数 → 结算到期预测 → 特征 → 四项预测 → 策略 → 风控 → 落库。
全部预测（包括未开仓的及其原因）写入 `predictions` 表。

- 线上版本切换后自动热加载；控制台修改风控/赔率后下一轮生效；
- 行情未更新到当前分钟、特征无效、计算超时，都会输出 NO_TRADE 并写明原因；
- 服务重启后从库中恢复未到期持仓和当日盈亏；
- `python -m becai.cli replay` 用历史数据回放整个实时流程，用来验证延迟和实时/离线一致性。

## 9. 任务、恢复与自动更新

- 训练/数据任务是独立子进程，日志落盘，状态在 SQLite；
- 流水线每个阶段完成后写检查点，Optuna 试验逐条落盘，候选模型的样本外预测逐个落盘 —— 中断后用同一个 run_id 重跑即从断点继续；
- 调度器：每日数据更新、每 N 天再训练、训练异常中断后自动恢复（最多 3 次）；
- **冠军/挑战者**：新版本与线上版本在同一个新测试窗口上比较（旧版本在该窗口上同样是样本外），更优才自动上线；
  可在控制台手动上线或一键回退。

## 10. 计算资源分配（96GB 显存 / 22 核 / 110GB 内存）

| 资源 | 分配 |
|---|---|
| CPU 0–3 | 实时预测服务专用 |
| CPU 其余 | 训练（LightGBM 16 线程、数据加载、特征构建） |
| GPU | 训练独占：XGBoost + 全部神经网络，可 4 个试验并行 |
| 内存 | 特征矩阵以只读内存映射共享给各并行进程（每币种约 4GB） |

序列窗口在 GPU 上按索引即时抽取（整段通道张量常驻显存），不做磁盘预切片。
